# Personal Linux workspace

## Problem Statement

The primary user runs independent terminal AI agents and works with project files on Fedora. Routine work includes launching agents, switching projects, inspecting changes, editing Markdown and configuration/code files, reviewing Git history and diffs, and reading generated documents or media. Moving between a terminal, file manager, editor and preview applications adds friction even though the user rarely writes code manually.

Terax already combines much of this workflow, but also includes built-in AI, provider and credential management, AI editing and supervision, voice, language servers, and distribution support the user does not want to maintain. Removing these features carelessly would break retained functionality because file access, Markdown, notifications, agent hooks, command execution and native wrappers share infrastructure with them.

The goal is a maintainable, personal-use-first public Linux fork with a cohesive workflow and demonstrated resource efficiency. Feature deletion or lazy loading alone is not evidence of lower startup cost, memory use or package size. The fork must protect unsaved work and active processes while remaining practical to update from upstream.

## Solution

Build a Linux x86-64 workspace around independently installed external agents, preserving the Ghostty-based terminal, Spaces, file management, CodeMirror editing, all existing Git capabilities, themes and customization. Remove only the explicitly selected built-in AI, voice, language-server and non-Linux build/distribution features, together with settings and dependencies exclusively used by them.

Make retained capabilities usable and safe: provide modest worktree/checkpoint controls, manual optionally named checkpoints, explicit file-conflict choices, opt-in recovery drafts, guarded Space/tab/application closure, and capability-specific agent integrations. Agent permission approval stays in each agent's terminal. Spaces organize project contexts and do not isolate files or processes.

Provide reading-oriented document previews for Markdown, PDF, images, audio/video and text/code. Load optional capabilities on demand, bound reads and decoded resources, explain unsupported formats and oversized files, stop unnecessary hidden work, and release tab-owned resources on close. Preserve web previews as a separate feature, unloading their frames immediately when hidden and making the reload/state-loss behavior clear.

Validate Fedora first, distribute RPM/DEB packages and an Arch recipe, and publish authenticated stable releases through checked tag-driven workflows. Check for updates automatically, ask before downloading or installing, and use validated dependency-resolving package tooling or the explicitly accepted package-tool handoff. Never automatically restart the application or interrupt agents to update it.

## Implementation Decisions

- **Product boundary and priority.** Preserve the complete explicit keep scope. Resolve tradeoffs in this order: protection of files/unsaved work/processes, terminal correctness, usable retained review/editing, resource efficiency, convenience/polish. The fork is personal-use-first with best-effort public support; package production does not imply broad desktop/distribution compatibility.
- **Selected removals.** Remove built-in AI chat, provider/model configuration, API-key management, tools, subagents, conversation storage, AI completion/edit review/Ask AI, voice, built-in supervision, language-server integration, and Windows/macOS/WSL/Nix build/distribution support. Remove settings and dependencies only when exclusive to those features. Removing application AI credentials does not remove external-agent or Git authentication.
- **Shared ownership boundaries.** Extract or retain shared native wrappers, file-access checks, Markdown rendering, notification routing, hooks, CLI/control infrastructure and shell-command support before deleting former owners. Markdown's use of AI-named components or Streamdown does not authorize removing its renderer. External formatters must retain their required command backend. Ordinary explicit editing and automatic preview reads retain distinct access policies.
- **Architecture continuity.** Retain Tauri/Rust OS ownership, React/TypeScript composition and CodeMirror basic editing. Keep new domain logic dependency-light and command/components thin. Prefer existing module and command contracts over unrelated rewrites. Existing themes, customization and unselected optional features remain.
- **Terminal core.** Keep the active adapted Ghostty WASM bridge compiled against pinned official Ghostty source, with SIMD/scalar artifacts and provenance/license requirements. The separate official-ABI evaluation is not the active runtime and is not a selected migration. Ghostty updates may require bridge adaptation, recompilation and compatibility/resource testing. Preserve terminal model/process ownership and renderer fallback while measuring Linux-specific behavior rather than assuming macOS findings transfer unchanged.
- **External-agent capabilities.** Validate OpenCode, Claude Code, Codex and terminal Antigravity CLI launch/basic terminal behavior; distinguish the Antigravity GUI command. Preserve existing integrations for other agents unless explicitly removed. Publish a per-agent capability matrix covering launching, process status, structured events, notifications and control. No particular vendor event vocabulary is assumed universal. Existing compatibility claims must be tested against actual supported versions; an installed version alone is not certification.
- **Hooks and permissions.** Hooks are separately opt-in, with before/after review, stale-file refusal and fork-owned configuration markers. Activation/trust instructions are agent-specific. Removal touches only this fork's entries, including during coexistence with upstream. Keep existing CLI/control and permission-response infrastructure, but leave version-one approvals in agent terminals with the appropriate fallback when no UI consumer exists. New centralized approval UI and new structured OpenCode/Antigravity adapters are deferred; Antigravity CLI launch/basic status is included.
- **Notifications.** Retain hidden-Space attention/completion routing without focus stealing. Default content is agent/Space identity and event type, without prompts, file contents or transcripts; sound defaults off and duplicate/rate suppression remains. Status labels must reflect available evidence rather than implying turn-level certainty from process lifecycle alone.
- **Spaces and process ownership.** A Space is named organization with a project root and saved tabs/layout, not a sandbox. Multiple Spaces may share a checkout with that relationship indicated. Switching preserves running terminal work while suppressing unnecessary presentation. Keep switching, closing tabs, deleting saved organization, removing a worktree and deleting project files distinct. Closing/deleting must handle dirty buffers and active/uncertain processes; Space deletion never implies project/worktree directory deletion.
- **Shutdown and restoration.** Summarize work and permit cancellation before quit. After confirmation, try graceful termination and ask before forcing remaining app-owned work to exit. Do not promise lifecycle control of deliberately detached external services. Layout restoration restores organization, directories and file locations without recreating live processes or automatically executing previous agent commands. A CLI's independent resume capability is not application-level process persistence.
- **Editing and conflicts.** Preserve syntax highlighting, find/replace, line-ending/indentation behavior and editor themes. Deliberately opened accessible files may lie outside the project root. Refresh clean buffers when visible; preserve dirty text on external changes. Compare, save elsewhere, reload/discard and overwrite are explicit conflict choices, with a fresh disk-version check before writes. Do not claim atomic exclusion of independent external writers.
- **App-owned mutation coordination.** Coordinate writes by canonical file identity and compare the expected disk revision inside native write coordination; the revision must distinguish same-mtime content changes. Competing buffers cannot both successfully overwrite the same baseline. Explicit overwrite consent applies to the reviewed disk revision and expires on subsequent change. Missing, unreadable or replaced targets produce an explicit conflict/error rather than unconditional recreation. Coordinate relevant app-initiated save/format sequences. For destructive Git/worktree operations, find affected file/worktree usage across all Spaces/panes, including outside-root editors, and recheck immediately before mutation. Prevent new conflicting app-owned saves, spawns and mutations during execution, or invalidate confirmation and refuse. Force does not silently bypass unsaved-buffer protection. Independent external writers remain outside guaranteed atomic exclusion.
- **Recovery drafts.** Add opt-in durable unsaved-text recovery, distinct from layout persistence and autosave of original files. Initial policy is 10 MiB per file and 100 MiB total in private local storage, with known-sensitive-path exclusions and visible unavailable/full states. Filename policy is not complete secret detection. Pause recovery rather than silently evict unrecovered drafts; remove resolved drafts after explicit successful save/discard. Changed, missing or moved targets require recovery-document comparison/Save As; recovery never reruns agents or writes project files automatically. Autosave, where retained/enabled, remains a separate action on the original file.
- **Recovery ownership and acknowledgement.** Preserve independent editor buffers. A recovery record carries stable buffer identity, original-file identity and distinguished revisions; path alone is not its owner. Save/discard cleanup resolves only that buffer revision, never newer or unrelated drafts. Late persistence completions neither overwrite newer records nor resurrect discarded drafts. Save As retargets only after success and preserves newer unsaved edits. A successful save of older text cannot cause save-and-close to discard newer typing. While storage and the application are healthy, coalescing schedules recovery persistence within two seconds during continuous editing rather than waiting indefinitely for idle. Only successfully durable revisions are acknowledged; pending, failed and unavailable states are visible. I/O stalls can delay acknowledgement, and crashes may lose newer, unacknowledged text. Quit uses a bounded flush; failure offers retry/cancel or explicit close-with-loss, and a second close event is not consent to loss. Preserve an older valid recovery record when a newer write fails.
- **Git and worktrees.** Preserve the full existing Git command and review surface, including hunk-level behavior and history. Keep Git review separate from removed AI review. Provide modest UI for existing worktree create/remove and checkpoint operations. New worktrees can open as separate Spaces without relocating existing terminals. Maintain authorization, path/ref guards, collision handling, worktree blockers and mutation integrity. Commit and push remain explicitly user initiated; destructive actions identify affected paths and blockers.
- **Checkpoint semantics.** Checkpoints are manual, optionally named, worktree-specific snapshots independent of agent turns. Use noncolliding identities rather than replacing recovery points by reusing a task/turn slot. Capture tracked and nonignored files without changing HEAD or the real index during creation; disclose ignored files, submodule contents, staging state and non-atomic/incomplete capture limitations. Bound snapshot creation and report storage pressure.
- **Checkpoint restore and cleanup.** Require resolution of affected unsaved/staged changes and relevant active agent work before restore; show touched paths, effects on staging, changed-HEAD concerns and external concurrency limitations. Keep restore safety snapshots but do not promise full Git-state undo or atomic restoration. Surface partial failures. Retain checkpoints until explicit deletion; make grouped cleanup and safety refs visible separately, including any safety refs a cleanup would remove. Do not automatically run Git garbage collection or equate deleted refs with exact reclaimed bytes.
- **Checkpoint removal and preflight.** Refuse worktree removal while its checkpoints or restore-safety refs remain; show the recovery points and require their explicit deletion before removal, or allow cancellation. Cleanup affects only the intended worktree's refs. Restoring archived checkpoints after worktree deletion is deferred. If a required safety snapshot cannot preserve affected content or publish its recovery ref, including because of limits or inconsistent capture, refuse before changing files or staging. Force cannot bypass this precondition. For failures after mutation starts, retain the safety ref, report partial effects, and require a fresh preview before retry rather than blindly repeating the old plan.
- **Document previews.** Initial categories are rendered Markdown, PDF, images, audio/video and text/code; CSV/TSV remain editable text. PDF must support navigation, zoom, search and selection in the actual Fedora application. Retain iframe rendering only if it satisfies reliability, reader-function and resource requirements; otherwise use a dedicated on-demand viewer. Image/media containers and codecs require actual package-environment tests and clear unsupported/error states, without automatic codec installation.
- **Preview access boundaries.** Document content does not execute application commands or automatically fetch remote resources. External navigation and remote-resource loading require deliberate action. Automatic local resources are anchored to the configured Space project root, or an outside document's directory, rather than mutable terminal cwd. Preserve native canonical containment and symlink checks; outside resources require explicit grants. Keep explicit single-file selection distinct from automatic directory-based embedding.
- **Web previews.** Preserve deliberately entered HTTP(S) web/dev-server previews as untrusted web content without native command access. Validate initial URL restrictions and browser/navigation boundaries; redirects/popups require actual boundary testing, not assumptions from initial URL validation. Hidden means an inactive tab/Space or a window reported hidden/minimized by supported visibility signals. Unload frames immediately for those states and explain reload/transient-state loss; mere focus loss while still visible does not unload a frame. Do not promise complete Linux occlusion detection. Frame teardown does not terminate the independent server process. This lifecycle differs from terminal models that must keep consuming output.
- **Resource contracts.** Optional editors/viewers load on demand. Bound native reads, outstanding operations and decoded/rendering resources, with explicit failure/override behavior within hard ceilings. Pause unnecessary hidden document presentation/playback and release tab-owned resources and grants on close; bound shared resources according to their ownership instead of destroying still-needed window resources. The starting text limits are 10 MiB normally, explicit override up to 50 MiB, and syntax features disabled above 4 MiB. Do not retain whole-file non-range asset allocation as an unexamined path around resource limits.
- **Measurement gates.** Start with a provisional two-Space/four-terminal/two-busy-agent workflow, several text files and one active preview, plus a separately described stress workload. These are accepted benchmark assumptions, not observed usage. Measure cold/warm startup, whole-application process memory, idle/streaming/hidden/close-cycle behavior and package size. Account separately for external-agent processes and avoid double-counting shared memory. Propose concrete document/decoded-resource and performance ceilings from baseline evidence and obtain user approval before claiming lightweight completion; no unmeasured numeric RAM/startup target is introduced here.
- **Fork identity.** Use independent application/storage identities, hook ownership markers, release endpoint and signing keys. Complete application, storage/cache, control-descriptor, shell-integration and hook namespace isolation is a prerequisite for every nonisolated developer or normal run, not just publication; changing the application ID alone is insufficient. Inventory shared names and preserve upstream-owned state. Read-only work and isolated temporary-profile baselines may proceed while final branding is deferred. Do not silently import, overwrite or delete upstream state. Any future import is explicit. Final product name, release owner/URL and key provisioning remain deliberate pre-publication decisions, not inferred from the Git remote or supplied with placeholder upstream identity.
- **Platform and package contract.** Initial architecture is Linux x86-64 with RPM, DEB and an Arch recipe. Primary validation is Fedora 44 KDE Plasma on Wayland; Debian 13 requires an actual graphical WebKitGTK session; Arch uses a dated clean environment and records package versions. Other desktops/releases are best-effort until tested. Remove non-Linux workflows/packaging first and retain useful inert portability seams when they reduce upstream-import cost.
- **Releases.** CI validates changes; version tags trigger stable release publication subject to passing checks, tag/application-version agreement, authenticated artifacts and install/upgrade evidence for the actual distributed artifacts. A tag alone is not successful validation. Preserve useful tests before deleting their platform jobs. No prerelease product channel is required initially. Final identity and independent trust provisioning block publication.
- **Updating and trust.** Check automatically with bounded, nonblocking behavior; obtain approval before package download or installation. Defer installation until running work and unsaved buffers are resolved and never automatically relaunch. RPM/DEB integration must use validated dependency-resolving package tooling with acceptable privilege, cancellation, dependency, package-lock and upgrade behavior. The locked plugin's direct rpm/dpkg paths are not sufficient evidence. If that integration is unavailable, provide the accepted explicit package-tool handoff. Arch remains package-tool managed. Verification failure blocks installation; failed transactions receive explicit recovery rather than unvalidated automatic rollback. Keep signing secrets outside the repository with offline recovery and documented key replacement. Artifact verification and native package/repository trust are distinct; managed package repositories are deferred.
- **Update installation interval.** Readiness checked before download is not sufficient. Recheck immediately before an app-owned package transaction; work started during download or delayed approval invalidates readiness. Before handing control to privilege/installation, prevent new conflicting app work throughout that interval, or abort before invoking the package tool. If the selected integration cannot enforce that contract, use the accepted package-tool handoff after safe closure. Distinguish available, handed-off and installed outcomes; handoff alone is never reported as successful installation. External package-manager actions are outside application enforcement. Cancellation and failure do not authorize relaunch or automatic rollback.
- **Maintenance and completeness.** Keep an upstream Terax remote and selectively import relevant fixes. Preserve lockfiles, exact toolchain pins, reproducibility checks, lint/types/tests, terminal compatibility/soak checks and bundle/resource budgets. Dependency bots open reviewed PRs that pass checks before merging; separately monitor the Ghostty revision where ecosystem tooling does not cover it. Review upstream/dependencies monthly and triage security fixes promptly. Build in stages while preserving a working Linux app; stages do not silently defer accepted version-one additions. Broader removals or reduction of accepted completion work require the user's decision.

## Testing Decisions

- **Approved primary seam.** The user approved one primary acceptance seam through the real Linux Tauri application, adapting the existing real-app lab and PTY-smoke approach. Exercise actions through application workflows and observe file contents, Git state, processes, rendered behavior, notifications and resource reports. ## Out of Scope

- Supporting a large user base or promising untested Linux distributions/desktops.
- Windows, macOS, WSL and Nix build/distribution support, and Linux architectures beyond x86-64 initially.
- Retaining or replacing the selected built-in AI, voice, AI editing/supervision or language-server features.
- Treating Spaces as sandboxes or guaranteeing isolation between agents sharing a checkout.
- Preserving live processes across app restarts, automatically rerunning previous commands, or embedding the Antigravity GUI.
- A new centralized agent-permission UI, automatic per-agent-turn checkpoints, and new structured OpenCode/Antigravity adapters in version one.
- Office document/spreadsheet rendering, dedicated CSV/TSV table previews, PDF annotation, document authoring through previews, or media editing.
- Unlimited large-file/decoded-resource handling, automatic codec installation, or universal support claims based on extension recognition.
- A new arbitrary-code plugin framework, broad customization-system rewrite, unrelated architectural rewrites, or removal of optional features still on watch.
- Automatic commits/pushes, silent destructive Git cleanup, automatic Git garbage collection, full-backup checkpoint claims or atomic exclusion of independent external writers.
- Archival checkpoint restoration after worktree deletion. Application-managed removal instead blocks until its checkpoints/safety refs are explicitly deleted. External deletion can still strand recovery metadata; reopen archival support if recovery across deleted worktrees becomes a requirement.
- Silent upstream data migration, shared upstream identity/trust keys, unsigned update bypasses, automatic application relaunch, unapproved downloads/installation or unvalidated rollback.
- Managed DNF/APT repositories and product prerelease channels initially.
- Inventing final branding, release ownership/URL, signing secrets, actual user workload counts, maintenance-hour commitments or unmeasured performance budgets.
- Implementing the product or decomposing this spec into implementation tickets as part of specification synthesis.
